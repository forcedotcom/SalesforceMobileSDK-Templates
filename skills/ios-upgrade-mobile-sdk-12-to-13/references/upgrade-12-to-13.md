# iOS — Upgrade Salesforce Mobile SDK 12.x to 13.2.1

Step-by-step guide for upgrading an existing iOS app from SDK 12.x to 13.2.1.

## Preconditions

- App already integrates Salesforce Mobile SDK 12.x (CocoaPods or SPM)
- Xcode 16 installed
- CocoaPods up to date (`gem install cocoapods` or `brew upgrade cocoapods`) if using CocoaPods

## Inputs

| Variable | Example | Notes |
|---|---|---|
| `<ProjectName>` | `MyApp` | Xcode project name (without `.xcodeproj`) |
| `<TargetName>` | `MyApp` | Main app target name |

---

## Step 0 — Detect project shape (CocoaPods vs SPM)

Before any file edits, determine which dependency manager is in use. Run a directory listing of the project root, then pick exactly one path:

| If you find… | Path |
|---|---|
| `Podfile` at the project root | CocoaPods — follow the **[CocoaPods]** sub-steps below |
| `Package.swift` at the project root, or `.xcodeproj/project.xcworkspace/xcshareddata/swiftpm/Package.resolved` | SPM (standalone manifest) — follow the **[SPM Option A]** sub-steps below |
| `XCRemoteSwiftPackageReference` inside `<ProjectName>.xcodeproj/project.pbxproj` only (no separate `Package.swift` or `Package.resolved`) | SPM (Xcode-native) — follow the **[SPM Option C]** sub-steps below |
| Both `Podfile` and `Package.swift` | CocoaPods takes precedence; the `Package.swift` is likely a library manifest, not the app integration |

State your choice before continuing: *"CocoaPods — found `Podfile`"*, *"SPM Option A — found `Package.resolved`"*, or *"SPM Option C — version pinned in project.pbxproj"*.

**Files modified per path:**

- **CocoaPods**: `Podfile`, `Podfile.lock`, `.xcworkspace` (regenerated by `pod install`), app source files
- **SPM (Option A)**: `Package.swift`, `Package.resolved`, app source files
- **SPM (Option C)**: `<ProjectName>.xcodeproj/project.pbxproj`, app source files

## Step 1 — Bump SDK version

### [CocoaPods]

Open `Podfile` and update all Salesforce Mobile SDK pods to `13.2.1`. Only update pods that are already present — do not add pods that were not in the file before.

**Case A — version-pinned Podfile** (pods declared as `pod 'SalesforceSDKCore', '12.x'`):

Before:
```ruby
source 'https://cdn.cocoapods.org/'
source 'https://github.com/forcedotcom/SalesforceMobileSDK-iOS-Specs'

platform :ios, '16.0'

target '<TargetName>' do
  use_frameworks!
  pod 'SalesforceSDKCore', '12.x'
  pod 'SalesforceAnalytics', '12.x'    # if present
  pod 'SalesforceSDKCommon', '12.x'    # if present
  pod 'SmartStore', '12.x'             # if present
  pod 'MobileSync', '12.x'             # if present
end
```

After:
```ruby
source 'https://cdn.cocoapods.org/'
source 'https://github.com/forcedotcom/SalesforceMobileSDK-iOS-Specs'

platform :ios, '17.0'

target '<TargetName>' do
  use_frameworks!
  pod 'SalesforceSDKCore', '13.2.1'
  pod 'SalesforceAnalytics', '13.2.1'  # if it was present before
  pod 'SalesforceSDKCommon', '13.2.1'  # if it was present before
  pod 'SmartStore', '13.2.1'           # if it was present before
  pod 'MobileSync', '13.2.1'           # if it was present before
end

post_install do |installer|
  installer.pods_project.targets.each do |target|
    target.build_configurations.each do |config|
      config.build_settings['IPHONEOS_DEPLOYMENT_TARGET'] = '17.0'
    end
  end
end
```

The deployment target bump in the `post_install` block prevents CocoaPods pods from being built against a lower deployment target than the app.

**Case B — `use_mobile_sdk!` helper Podfile** (generated by `forceios create` / `forceios createwithtemplate`):

The generated Podfile uses `use_mobile_sdk!` from a local helper at `mobile_sdk/SalesforceMobileSDK-iOS/mobilesdk_pods.rb` and does not have explicit version strings. In this case:

1. Update `platform :ios, '16.0'` → `platform :ios, '17.0'` in the Podfile.
2. The `use_mobile_sdk!` macro pulls in the SDK from the local cloned copy in `mobile_sdk/`. To upgrade the SDK version, update the `mobile_sdk` submodule (or replace the local clone) to tag `v13.2.1`:
   ```bash
   git -C mobile_sdk/SalesforceMobileSDK-iOS fetch --tags
   git -C mobile_sdk/SalesforceMobileSDK-iOS checkout v13.2.1
   ```
3. After checking out v13.2.1, `mobile_sdk/SalesforceMobileSDK-iOS/mobilesdk_pods.rb` already contains `change_deployment_target(target, '17.0')` for SDK targets — no manual edit needed.

**Verify before running `pod install`.** Confirm:
- `platform :ios` is `'17.0'`
- If using Case A: all `12.x` version strings are replaced with `13.2.1`
- If using Case B: `mobile_sdk/SalesforceMobileSDK-iOS` is checked out at `v13.2.1`
- The `post_install` block sets `IPHONEOS_DEPLOYMENT_TARGET` to `'17.0'` (or the helper does it)

### [SPM Option A — standalone `Package.swift`]

Update the version requirement for `SalesforceMobileSDK-iOS-SPM`:

Before:
```swift
.package(url: "https://github.com/forcedotcom/SalesforceMobileSDK-iOS-SPM", from: "12.0.0"),
```

After:
```swift
.package(url: "https://github.com/forcedotcom/SalesforceMobileSDK-iOS-SPM", from: "13.2.1"),
```

Also update the platforms declaration (Step 2 below).

### [SPM Option B — Xcode UI only]

Use Xcode → File → Packages → Update to Latest Package Versions, then pin the version to `13.2.1` in the package dependency settings.

### [SPM Option C — version pinned in `project.pbxproj`]

When the app was added to Xcode via the "Add Package Dependencies" dialog without a standalone `Package.swift`, Xcode stores the version pin directly in `project.pbxproj` as an `XCRemoteSwiftPackageReference` block. There is no `Package.resolved` file to update separately.

Find the block:
```
/* Begin XCRemoteSwiftPackageReference section */
...
    repositoryURL = "https://github.com/forcedotcom/SalesforceMobileSDK-iOS-SPM";
    requirement = {
        kind = exactVersion;
        version = 12.2.0;
    };
...
/* End XCRemoteSwiftPackageReference section */
```

Update `version = 12.2.0` to `version = 13.2.1`. If `kind = upToNextMajorVersion`, update `minimumVersion = 12.0.0` to `minimumVersion = 13.2.1` instead.

After editing, run `xcodebuild -resolvePackageDependencies` (Step 3) to fetch the new version.

## Step 2 — Raise iOS deployment target to 17.0

SDK 13 requires iOS 17.0. Update the deployment target in **both** the dependency manifest and the Xcode project — they must match.

### Podfile / Package.swift

**CocoaPods:** Already updated in Step 1 (`platform :ios, '17.0'` and `post_install` block).

**SPM (`Package.swift`):** Update the platforms line:

Before:
```swift
platforms: [.iOS(.v16)],
```

After:
```swift
platforms: [.iOS(.v17)],
```

### Xcode project (`project.pbxproj`)

The deployment target must be raised in the Xcode project for **every** build configuration that explicitly sets it. Targets that do not have an explicit `IPHONEOS_DEPLOYMENT_TARGET` entry inherit from the project-level setting — updating the project-level entry is sufficient for those targets.

Check the current value:

```bash
grep -r 'IPHONEOS_DEPLOYMENT_TARGET' <ProjectName>.xcodeproj/project.pbxproj
```

Update all occurrences to `17.0`. The safest approach for a hand-maintained `.xcodeproj` is to use Xcode's Build Settings editor (select the project, select each target, find iOS Deployment Target, change to 17.0). For an xcodegen-managed project, edit `project.yml` and set `deploymentTarget.iOS: '17.0'` on each target, then run `xcodegen generate`.

> If `grep` returns no `IPHONEOS_DEPLOYMENT_TARGET` entries for a particular target, that target inherits from the project-level setting — updating only the project-level entries is sufficient for those targets.

**Verify:** After updating, grep confirms no remaining `16.0` references in the deployment target:

```bash
grep 'IPHONEOS_DEPLOYMENT_TARGET' <ProjectName>.xcodeproj/project.pbxproj | grep -v '17.0'
# Expected: no output
```

## Step 3 — Run `pod install` / SPM resolve

### [CocoaPods]

**Case B (`use_mobile_sdk!`) only — delete `Podfile.lock` before installing:**

```bash
rm Podfile.lock
```

The existing lock file pins SQLCipher at `4.6.1`. SDK 13.2.1's SmartStore requires `~> 4.10.0`. CocoaPods cannot satisfy both constraints simultaneously — it will abort with `[!] CocoaPods could not find compatible versions for pod "SQLCipher"` unless the lock is removed first. CocoaPods regenerates the lock file with the correct `4.10.x` version on the next install.

(Case A version-pinned Podfiles do not need this step — CocoaPods resolves the new explicit versions without a lock conflict.)

```bash
pod install --repo-update
```

Run from the project root (the directory containing the `Podfile`). The `--repo-update` flag refreshes the Salesforce specs repo and is required when bumping major versions.

Expected output: `Pod installation complete!` with no errors. `Podfile.lock` is updated to reflect `13.2.1`. The `.xcworkspace` is regenerated.

If you see `[!] CocoaPods could not find compatible versions for pod "SalesforceSDKCore"`, the Salesforce specs source is missing from the Podfile — add both sources from the Step 1 template above.

### [SPM]

In Xcode: **File → Packages → Resolve Package Versions**

Or from the command line:

```bash
xcodebuild -resolvePackageDependencies \
  -project <ProjectName>.xcodeproj \
  -scheme <TargetName>
```

Expected: `Package resolution completed successfully.`

## Step 4 — Fix compilation errors

Build the project to surface all errors, then fix them by category. Run:

```bash
xcodebuild build \
  -workspace <ProjectName>.xcworkspace \
  -scheme <TargetName> \
  -destination 'platform=iOS Simulator,OS=17.0,name=iPhone 16' \
  2>&1 | grep -E 'error:|note:'
```

(Use `-project` instead of `-workspace` for SPM builds without CocoaPods.)

### 4a. Removed crypto methods

`SFSDKCryptoUtils` dropped its RSA convenience wrappers. Replace with the Security framework directly:

```objc
// BEFORE
NSData *encrypted = [SFSDKCryptoUtils encryptUsingRSAforData:data withKeyRef:keyRef];
NSData *decrypted = [SFSDKCryptoUtils decryptUsingRSAforData:data withKeyRef:keyRef];

// AFTER
NSData *encrypted = (__bridge_transfer NSData *)SecKeyCreateEncryptedData(
    keyRef,
    kSecKeyAlgorithmRSAEncryptionOAEPSHA1,
    (__bridge CFDataRef)data,
    NULL
);
NSData *decrypted = (__bridge_transfer NSData *)SecKeyCreateDecryptedData(
    keyRef,
    kSecKeyAlgorithmRSAEncryptionOAEPSHA1,
    (__bridge CFDataRef)data,
    NULL
);
```

Add `#import <Security/Security.h>` (Obj-C) or `import Security` (Swift) if not already imported.

### 4b. Removed `SFApplicationHelper.openURL:`

The single-argument `openURL:` variant was removed. Replace with the options-bearing form:

```objc
// BEFORE
[SFApplicationHelper openURL:url];

// AFTER
[SFApplicationHelper openURL:url options:@{} completionHandler:nil];
```

Swift:

```swift
// BEFORE
SFApplicationHelper.open(url)

// AFTER
SFApplicationHelper.open(url, options: [:], completionHandler: nil)
```

### 4c. `SFSDKOAuthProtocol.revokeRefreshToken:reason:` is now required

This method was `@optional` in SDK 12. In SDK 13 it is `@required`. Any class that conforms to `SFSDKOAuthProtocol` will fail to compile unless this method is implemented.

Add the implementation to every conforming class:

```objc
// Objective-C
- (void)revokeRefreshToken:(SFOAuthCredentials *)credentials reason:(SFLogoutReason)reason {
    [self.coordinator revokeRefreshToken:credentials reason:reason];
}
```

```swift
// Swift
func revokeRefreshToken(_ credentials: SFOAuthCredentials, reason: SFLogoutReason) {
    coordinator.revokeRefreshToken(credentials, reason: reason)
}
```

If your conforming class does not hold a coordinator reference, forward to `SalesforceManager.shared`:

```swift
func revokeRefreshToken(_ credentials: SFOAuthCredentials, reason: SFLogoutReason) {
    SalesforceManager.shared.logout()
}
```

### 4d. Removed classes — remove all usages

These classes no longer exist in SDK 13. Search for each and remove:

| Removed class / member | Action |
|---|---|
| `SFCrypto.baseAppIdentifier` | Remove call; the concept is now internal to the SDK |
| `SFCrypto.baseAppIdentifierIsConfigured` | Remove call |
| `SFCrypto.baseAppIdentifierConfiguredThisLaunch` | Remove call |
| `SFSDKAppDelegate` | Remove conformance from `AppDelegate`; the SDK no longer requires it |
| `SFSDKNewLoginHostViewController` | Remove any direct instantiation; the SDK manages this internally |
| `SalesforceSDKManager.isQrCodeLoginEnabled` | Remove; QR login is now always enabled |

Search for usages:

```bash
grep -rn 'SFCrypto\|SFSDKAppDelegate\|SFSDKNewLoginHostViewController\|isQrCodeLoginEnabled' \
  --include='*.swift' --include='*.m' --include='*.h' .
```

> **Generated apps (`forceios create`):** `isQrCodeLoginEnabled` appears inside `setupQrCodeLogin()` in `AppDelegate.swift`. Remove the line `MobileSyncSDKManager.shared.isQrCodeLoginEnabled = true` and its preceding `// Enable QR code log in.` comment. The method itself (`setupQrCodeLogin()`) can stay — it is only called when QR login is explicitly wired up, which is commented out by default in the generated template.

### 4e. Removed header imports

These headers no longer exist in SDK 13. Remove the corresponding `#import` lines:

```objc
// Remove these lines:
#import <SalesforceSDKCore/SFSDKWebViewStateManager.h>
#import <SalesforceSDKCore/SFSDKDevInfoViewController.h>
```

The Swift class `SFSDKWebViewStateManager` is still available — call it directly in Swift without importing a header:

```swift
SFSDKWebViewStateManager.removeSession()
```

### 4f. Push notification API changes (if using push)

`PushNotificationManager` was rewritten in Swift in SDK 13.1. The public API is **source-compatible**: your existing calls will still compile and run on SDK 13.2.1. No code change is required for the upgrade.

The **preferred** SDK 13 API uses `completionBlock` / `failBlock` callbacks and returns `Bool` (`@discardableResult`):

**Swift (preferred — SDK 13):**

```swift
// Preferred form:
SFPushNotificationManager.sharedInstance().registerSalesforceNotifications(
    completionBlock: {
        // registration succeeded
    },
    failBlock: {
        // registration failed
    }
)

// With a specific user account:
SFPushNotificationManager.sharedInstance().registerSalesforceNotifications(
    for: userAccount,
    completionBlock: { /* success */ },
    failBlock: { /* failure */ }
)
```

**Swift (legacy — still works in SDK 13.2.1):**

```swift
// Legacy Result<Bool, PushNotificationManagerError> form — still present in 13.2.1:
SFPushNotificationManager.sharedInstance().registerForSalesforceNotifications { result in
    switch result {
    case .success: break
    case .failure(let error): print(error)
    }
}
```

**Objective-C:**

```objc
// Preferred Obj-C selector (SDK 13):
[SFPushNotificationManager.sharedInstance
    registerSalesforceNotificationsWithCompletionBlock:^{
        // success
    }
    failBlock:^{
        // failure
    }];

// Unregister:
[SFPushNotificationManager.sharedInstance
    unregisterSalesforceNotificationsWithCompletionBlock:^{
        // done
    }];
```

If you have no push code, skip this step. If the compiler reports "no visible interface" for a push selector, verify you are importing `SalesforceSDKCore` and that your target links the framework.

## Step 5 — Fix runtime and behavioral changes

### 5a. `SFLogoutReason` integer values shifted

Do not persist the `rawValue` of `SFLogoutReason` to disk. The integer backing values changed between SDK 12 and 13. If your app serializes logout reasons to `UserDefaults`, a database, or a file, those stored values will be misinterpreted after upgrade.

Migration:
1. On first launch after upgrade, clear any stored `SFLogoutReason` `rawValue` integers.
2. Always compare using the enum constant, never the raw integer:

```swift
// Correct
if reason == .tokenExpired { ... }

// Wrong — breaks across SDK versions
if reason.rawValue == 1 { ... }
```

### 5b. `bootConfigRuntimeSelector` renamed to `appConfigForLoginHost` (SDK 13.2+)

If your app customizes the boot config at runtime based on the login host:

```swift
// BEFORE (SDK 13.0/13.1)
SalesforceSDKManager.shared.bootConfigRuntimeSelector = #selector(mySelector)

// AFTER (SDK 13.2+)
SalesforceSDKManager.shared.appConfigForLoginHost = { loginHost, callback in
    let config = myBootConfig(for: loginHost)
    callback(config)
}
```

The closure-based API eliminates the `@objc` selector requirement and is type-safe. If you were not using `bootConfigRuntimeSelector`, skip this step.

### 5c. SmartStore encryption — `fixFor530Bug` auto-heal removed (if using SmartStore)

SDK 13 removes the automatic database migration that healed stores created during the Mobile SDK 5.3.0 CocoaPods era (a specific encryption bug). If any of your users have databases that were created with Mobile SDK 5.3.0 and were never migrated, those databases will remain corrupt after upgrade.

This only affects apps that:
1. Were originally built against Mobile SDK 5.3.0 distributed via CocoaPods, AND
2. Have users whose device has **never** launched an app version built against SDK 5.3.1 through 12.x

If your app was first published after SDK 5.3.1, no action is required.

If your app was published during the 5.3.0 era, you need to verify on a **per-installation** basis, not per release: shipping an intermediate SDK version does not guarantee every active user ran it. Check your analytics to determine whether any current active installations could still be running a database created in the 5.3.0 era. If you cannot rule it out:

1. Add a first-launch-after-upgrade check (e.g. a versioned `UserDefaults` flag) that detects potentially-affected stores.
2. Either attempt a manual database repair using `SFSmartStore` repair APIs, or prompt the affected user to log out and log back in (which recreates the store from scratch after a fresh OAuth flow).

## Step 6 — Address deprecation warnings (removed in SDK 14.0)

These APIs are deprecated in SDK 13 and will be removed in 14.0. Fix them now to avoid a forced migration at the next major release:

**Instrumentation (remove entirely):**

```bash
grep -rn 'SFInstrumentation\|SFMethodInterceptor\|SFSDKInstrumentationHelper' \
  --include='*.swift' --include='*.m' .
```

Remove all usages. The instrumentation infrastructure is being replaced by a new diagnostic framework.

**OAuth session managing protocol (remove conformance):**

```swift
// BEFORE — deprecated (Swift)
class MyAuthCoordinator: SFSDKOAuthSessionManaging { ... }

// AFTER — remove the protocol; use the non-deprecated OAuth coordinator APIs
class MyAuthCoordinator { ... }
```

```objc
// BEFORE — deprecated (Obj-C)
@interface MyAuthCoordinator () <SFSDKOAuthSessionManaging>
@end

// AFTER — remove the protocol adoption
@interface MyAuthCoordinator ()
@end
```

**Shared process pool (migrate):**

```swift
// BEFORE — deprecated (Swift)
let pool = SFSDKWebViewStateManager.sharedProcessPool

// AFTER — manage your own WKProcessPool, or let the SDK manage it (SDK 15+ no longer honors this)
```

```objc
// BEFORE — deprecated (Obj-C)
WKProcessPool *pool = SFSDKWebViewStateManager.sharedProcessPool;

// AFTER — remove the reference; create your own WKProcessPool if needed
```

**REST client completion blocks (migrate to async/await):**

```swift
// BEFORE — deprecated block-based API
restClient.send(request: request) { response, urlResponse, error in
    guard error == nil else { return }
    // handle response
}

// AFTER — async/await (SDK 13)
Task {
    do {
        let response = try await restClient.send(request: request)
        // handle response
    } catch {
        // handle error
    }
}
```

The async/await API is available from iOS 15 and above. Since the new deployment target is iOS 17.0, no availability guard is required.

## Step 7 — Build verification

Run the full build. Expected: `** BUILD SUCCEEDED **`.

```bash
xcodebuild build \
  -workspace <ProjectName>.xcworkspace \
  -scheme <TargetName> \
  -destination 'platform=iOS Simulator,OS=17.0,name=iPhone 16' \
  | tail -5
```

For SPM builds (no CocoaPods):

```bash
xcodebuild build \
  -project <ProjectName>.xcodeproj \
  -scheme <TargetName> \
  -destination 'platform=iOS Simulator,OS=17.0,name=iPhone 16' \
  | tail -5
```

If the build fails, see the categorized fixes in [Step 4](#step-4--fix-compilation-errors), or consult [Troubleshooting](troubleshooting.md).
