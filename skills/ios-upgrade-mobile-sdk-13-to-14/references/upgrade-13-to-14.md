# iOS — Upgrade Salesforce Mobile SDK 13.x to 14.0

Step-by-step guide for upgrading an existing iOS app from SDK 13.x to 14.0.

## Preconditions

- App already integrates Salesforce Mobile SDK 13.x (CocoaPods or SPM)
- Xcode 16 installed
- CocoaPods up to date (`gem install cocoapods` or `brew upgrade cocoapods`) if using CocoaPods

## Inputs

| Variable | Example | Notes |
|---|---|---|
| `<ProjectName>` | `MyApp` | Xcode project name (without `.xcodeproj`) |
| `<TargetName>` | `MyApp` | Main app target name |

---

## Step 0 — Detect project shape

Before any file edits, determine which dependency manager and project generation strategy is in use. Run a directory listing of the project root, then pick exactly one path:

| If you find… | Path |
|---|---|
| `Podfile` at the project root | CocoaPods — follow the **[CocoaPods]** sub-steps below |
| `project.yml` at the project root | xcodegen + SPM — follow the **[xcodegen + SPM]** sub-steps below |
| `XCRemoteSwiftPackageReference` inside `<ProjectName>.xcodeproj/project.pbxproj` only (no `Podfile`, no `project.yml`) | Hand-managed SPM — follow the **[Hand-managed SPM]** sub-steps below |

State your shape choice before continuing: *"CocoaPods — found `Podfile`"*, *"Hand-managed SPM — found `XCRemoteSwiftPackageReference` in project.pbxproj"*, or *"xcodegen + SPM — found `project.yml`"*.

**Files modified per path:**

- **CocoaPods**: `Podfile`, `Podfile.lock`, `.xcworkspace` (regenerated by `pod install`), `project.pbxproj`, app source files
- **Hand-managed SPM**: `<ProjectName>.xcodeproj/project.pbxproj`, app source files
- **xcodegen + SPM**: `project.yml`, `<ProjectName>.xcodeproj/project.pbxproj` (regenerated by `xcodegen generate`), app source files

## Step 1 — Raise iOS deployment target to 18.0

SDK 14.0 requires iOS 18.0. This step applies to **all project shapes**.

### Xcode project (`project.pbxproj`)

Check current values:

```bash
grep 'IPHONEOS_DEPLOYMENT_TARGET' <ProjectName>.xcodeproj/project.pbxproj
```

Update every occurrence of `17.0` to `18.0`. The file typically has two entries (Debug and Release) at both the project level and each target level. Update all of them:

```bash
sd 'IPHONEOS_DEPLOYMENT_TARGET = 17.0' 'IPHONEOS_DEPLOYMENT_TARGET = 18.0' \
  <ProjectName>.xcodeproj/project.pbxproj
```

Verify no `17.0` deployment target entries remain:

```bash
grep 'IPHONEOS_DEPLOYMENT_TARGET' <ProjectName>.xcodeproj/project.pbxproj | grep -v '18.0'
# Expected: no output
```

> Skip editing `project.pbxproj` directly for the **xcodegen + SPM** path — `xcodegen generate` will rewrite it in Step 2. Set the deployment target in `project.yml` only (see Step 2).

### [CocoaPods] — Podfile

Update the platform declaration:

Before:
```ruby
platform :ios, '17.0'
```

After:
```ruby
platform :ios, '18.0'
```

Also update the `post_install` block if it sets `IPHONEOS_DEPLOYMENT_TARGET`:

```ruby
post_install do |installer|
  mobile_sdk_post_install(installer)
  installer.pods_project.targets.each do |target|
    target.build_configurations.each do |config|
      config.build_settings['IPHONEOS_DEPLOYMENT_TARGET'] = '18.0'
    end
  end
end
```

### [xcodegen + SPM] — project.yml

Update the deployment target for each target:

Before:
```yaml
deploymentTarget: "17.0"
```

After:
```yaml
deploymentTarget: "18.0"
```

## Step 2 — Update SDK version

> **Release candidate note:** The current published 14.0 artifact is the release candidate `14.0.0-rc.2`, not `14.0.0`. Use `14.0.0-rc.2` for every version pin (CocoaPods pods, SPM `exactVersion`, xcodegen `version`) until the GA release is published. Plain `14.0.0` is not in the Specs/SPM repos and will fail resolution (`pod install`: "no spec satisfying `SalesforceSDKCore (= 14.0.0)`").

### [CocoaPods] — Detect Podfile style before editing

First determine whether the Podfile uses explicit version strings or the `use_mobile_sdk!` helper:

```bash
grep -n 'use_mobile_sdk!\|pod .SalesforceSDKCore' Podfile
```

- **Case A — explicit version strings** (`pod 'SalesforceSDKCore', '13.x'` present): follow **[Case A]** below.
- **Case B — `use_mobile_sdk!` helper** (no explicit version strings; Podfile loads `mobilesdk_pods.rb` from a local `mobile_sdk/` clone): follow **[Case B]** below.

### [CocoaPods — Case A] Explicitly-versioned Podfile

Update all Salesforce Mobile SDK pods from `13.x` to `14.0.0-rc.2`. Only update pods that are already present — do not add pods that were not in the file before.

Before:
```ruby
source 'https://cdn.cocoapods.org/'
source 'https://github.com/forcedotcom/SalesforceMobileSDK-iOS-Specs'

platform :ios, '18.0'

target '<TargetName>' do
  use_frameworks!
  pod 'SalesforceSDKCore', '13.2.1'
  pod 'SalesforceAnalytics', '13.2.1'  # if present
  pod 'SalesforceSDKCommon', '13.2.1'  # if present
  pod 'SmartStore', '13.2.1'           # if present
  pod 'MobileSync', '13.2.1'           # if present
end

post_install do |installer|
  mobile_sdk_post_install(installer)
  signposts_post_install(installer)    # REMOVE THIS LINE
  installer.pods_project.targets.each do |target|
    target.build_configurations.each do |config|
      config.build_settings['IPHONEOS_DEPLOYMENT_TARGET'] = '18.0'
    end
  end
end
```

After:
```ruby
source 'https://cdn.cocoapods.org/'
source 'https://github.com/forcedotcom/SalesforceMobileSDK-iOS-Specs'

platform :ios, '18.0'

target '<TargetName>' do
  use_frameworks!
  pod 'SalesforceSDKCore', '14.0.0-rc.2'
  pod 'SalesforceAnalytics', '14.0.0-rc.2'  # if it was present before
  pod 'SalesforceSDKCommon', '14.0.0-rc.2'  # if it was present before
  pod 'SmartStore', '14.0.0-rc.2'           # if it was present before
  pod 'MobileSync', '14.0.0-rc.2'           # if it was present before
end

post_install do |installer|
  mobile_sdk_post_install(installer)
  installer.pods_project.targets.each do |target|
    target.build_configurations.each do |config|
      config.build_settings['IPHONEOS_DEPLOYMENT_TARGET'] = '18.0'
    end
  end
end
```

Key changes:
- Version bumped from `13.x` to `14.0.0-rc.2` on all SDK pods.
- `signposts_post_install(installer)` and its comment removed from `post_install`. Only `mobile_sdk_post_install(installer)` should remain.
- Both sources declared — `https://github.com/forcedotcom/SalesforceMobileSDK-iOS-Specs` is required for SQLCipher 4.17.0.

Verify before running `pod install`:
- `platform :ios` is `'18.0'`
- All `13.x` version strings replaced with `14.0.0-rc.2`
- `signposts_post_install(installer)` is removed
- Both sources declared at the top of the Podfile

Then run:

```bash
pod install
```

Expected: `Pod installation complete!`. `Podfile.lock` reflects `14.0.0-rc.2`. The `.xcworkspace` is regenerated.

### [CocoaPods — Case B] `use_mobile_sdk!` Podfile (generated by forceios)

Apps generated by `forceios create` / `forceios createWithTemplate` do not have explicit version strings in their Podfile. Instead the Podfile loads `mobilesdk_pods.rb` from a **local clone** at `mobile_sdk/SalesforceMobileSDK-iOS/`. The SDK version is determined by what that clone is checked out at.

**Step B-1: Update Podfile platform and remove signposts.**

In `Podfile`:
- Change `platform :ios, '17.0'` → `platform :ios, '18.0'`
- Remove `signposts_post_install(installer)` and its comment from the `post_install` block; keep `mobile_sdk_post_install(installer)` and any other `*_post_install` calls that are present (e.g. `vision_os_post_install(installer)`) — only `signposts_post_install` is removed

**Step B-2: Checkout the new SDK version in the local clone.**

```bash
git -C mobile_sdk/SalesforceMobileSDK-iOS fetch --tags
git -C mobile_sdk/SalesforceMobileSDK-iOS checkout v14.0.0-rc.2
```

Verify:
```bash
git -C mobile_sdk/SalesforceMobileSDK-iOS describe --tags
# Expected: v14.0.0-rc.2
```

**Step B-3: Remove the stale lock file and Pods directory, then reinstall.**

The existing `Podfile.lock` pins SQLCipher at `4.10.0` from the 13.x install. SDK 14.0 requires `~> 4.17.0`, which conflicts with the pinned version. A plain `pod install` will fail with:

```
[!] CocoaPods could not find compatible versions for pod "SQLCipher":
  In snapshot (Podfile.lock): SQLCipher (= 4.10.0, ...)
  In Podfile: SQLCipher (= 4.17.0)
```

Delete the stale lockfile and cached pods before installing:

```bash
rm -f Podfile.lock
rm -rf Pods/
pod install
```

Expected: `Pod installation complete!`. `Podfile.lock` now shows `14.0.0-rc.2` for all SDK pods (SalesforceSDKCore, SalesforceAnalytics, SalesforceSDKCommon, SmartStore, MobileSync) and SQLCipher `4.17.0`.

> **Multi-target apps** (e.g. apps with a widget or app extension target): Extension targets that reference the local clone via `:path => "./mobile_sdk/SalesforceMobileSDK-iOS"` automatically pick up the updated SDK version after the `git checkout` in Step B-2. No separate version changes are needed for those targets.

### [Hand-managed SPM] — project.pbxproj

The version is an `exactVersion` pin stored directly in `project.pbxproj`. Find the `XCRemoteSwiftPackageReference` block for `SalesforceMobileSDK-iOS-SPM`:

```
/* Begin XCRemoteSwiftPackageReference section */
...
    repositoryURL = "https://github.com/forcedotcom/SalesforceMobileSDK-iOS-SPM";
    requirement = {
        kind = exactVersion;
        version = 13.2.1;
    };
...
/* End XCRemoteSwiftPackageReference section */
```

Update `version = 13.2.1` to `version = 14.0.0-rc.2`:

```bash
sd 'version = 13.2.1;' 'version = 14.0.0-rc.2;' \
  <ProjectName>.xcodeproj/project.pbxproj
```

> If `kind = upToNextMajorVersion`, update `minimumVersion = 13.0.0` to `minimumVersion = 14.0.0-rc.2` instead. (An `upToNextMajorVersion` rule from `14.0.0-rc.2` still resolves the rc build, since no higher 14.x is published yet.)

No `Package.resolved` file exists in this shape — the pin lives entirely in `project.pbxproj`. No target membership edits are needed; the product list is unchanged.

Alternatively via Xcode UI: **File → Packages → Update To Latest Package Versions**, then verify the version resolves to 14.0.0-rc.2 in the Package Dependencies inspector.

After editing, resolve packages from the command line:

```bash
xcodebuild -resolvePackageDependencies \
  -project <ProjectName>.xcodeproj \
  -scheme <TargetName>
```

Expected: `Package resolution completed successfully.`

### [xcodegen + SPM] — project.yml

Update the version pin in the `packages` section:

Before:
```yaml
packages:
  SalesforceMobileSDK-iOS-SPM:
    url: https://github.com/forcedotcom/SalesforceMobileSDK-iOS-SPM
    version: 13.2.1
```

After:
```yaml
packages:
  SalesforceMobileSDK-iOS-SPM:
    url: https://github.com/forcedotcom/SalesforceMobileSDK-iOS-SPM
    version: 14.0.0-rc.2
```

Verify the target dependencies list references the required SDK products. SPM does not propagate transitive dependencies — all three must be explicit:

```yaml
dependencies:
  - package: SalesforceMobileSDK-iOS-SPM
    product: SalesforceSDKCore
  - package: SalesforceMobileSDK-iOS-SPM
    product: SalesforceAnalytics
  - package: SalesforceMobileSDK-iOS-SPM
    product: SalesforceSDKCommon
  # Add SmartStore and MobileSync here if the app uses them
```

Then regenerate the project and resolve packages:

```bash
xcodegen generate && \
xcodebuild -resolvePackageDependencies \
  -project <ProjectName>.xcodeproj \
  -scheme <TargetName>
```

Expected: `xcodegen` exits cleanly, then `Package resolution completed successfully.`

## Step 3 — Migrate SwiftUI PreviewProvider to #Preview macro (optional)

This step applies only if the app contains SwiftUI preview code using `PreviewProvider`. The old `PreviewProvider` pattern continues to compile — this migration is cosmetic and optional.

Before:
```swift
struct ContentView_Previews: PreviewProvider {
    static var previews: some View {
        ContentView()
    }
}
```

After:
```swift
#Preview {
    ContentView()
}
```

To find all `PreviewProvider` conformances in the project:

```bash
grep -rn 'PreviewProvider' --include='*.swift' .
```

Update each one if desired, or leave them as-is.

## Step 4 — Remove instrumentation classes (if used)

Check whether the app uses any of the instrumentation classes that were deprecated in SDK 13 and removed in SDK 14:

```bash
grep -rn 'SFInstrumentation\|SFMethodInterceptor\|SFSDKInstrumentationHelper' \
  --include='*.swift' --include='*.m' --include='*.h' .
```

If any matches are found:
- Remove all `import SFInstrumentation` statements and any `@import SalesforceSDKCore.SFInstrumentation` directives.
- Remove all calls to `SFMethodInterceptor` and `SFSDKInstrumentationHelper`.
- Remove any class or extension that subclasses or wraps these types.

If no matches: skip this step.

## Step 5 — Remove SFSDKOAuthSessionManaging conformance (if present)

Check whether any class conforms to `SFSDKOAuthSessionManaging`:

```bash
grep -rn 'SFSDKOAuthSessionManaging' --include='*.swift' --include='*.m' --include='*.h' .
```

If found, remove the protocol conformance declaration. The protocol was removed in SDK 14.

Swift:
```swift
// BEFORE
class MyAuthCoordinator: SFSDKOAuthSessionManaging { ... }

// AFTER — remove protocol adoption
class MyAuthCoordinator { ... }
```

Objective-C:
```objc
// BEFORE
@interface MyAuthCoordinator () <SFSDKOAuthSessionManaging>
@end

// AFTER
@interface MyAuthCoordinator ()
@end
```

Remove any methods that were required only to satisfy this protocol.

## Step 6 — Remove SFSDKWebViewStateManager.sharedProcessPool usage (if present)

Check for usage of the removed `sharedProcessPool` property:

```bash
grep -rn 'sharedProcessPool' --include='*.swift' --include='*.m' .
```

If found, remove the reference. If the code depended on sharing a `WKProcessPool` across web views, create and manage your own `WKProcessPool` instance:

```swift

let pool = SFSDKWebViewStateManager.sharedProcessPool

```

## Step 7 — Migrate SFOAuthSessionRefresher (deprecated; migrate when convenient)

`SFOAuthSessionRefresher` is **not removed** in SDK 14 — it is deprecated (`SFSDK_DEPRECATED(14.0, 15.0, ...)`) and scheduled for removal in a future release. Existing code still compiles, but migrate to the `UserAccountManager` refresh API.

Check whether the app directly instantiates `SFOAuthSessionRefresher`:

```bash
grep -rn 'SFOAuthSessionRefresher' --include='*.swift' --include='*.m' .
```

If found, replace with `UserAccountManager.refresh(credentials:)`:

```swift
// BEFORE (still compiles, but deprecated)
let refresher = SFOAuthSessionRefresher(credentials: credentials)
refresher.refreshSession { updatedCredentials in
    // handle success
} error: { error in
    // handle error
}

// AFTER — refresh(credentials:) uses a Result callback and returns Bool
let started = UserAccountManager.shared().refresh(credentials: credentials) { result in
    switch result {
    case .success(let (userAccount, authInfo)):
        // use userAccount / authInfo
        break
    case .failure(let error):
        // handle error
        break
    }
}

// Or the async form:
// let (userAccount, authInfo) = try await UserAccountManager.shared().refresh(credentials: credentials)
```

Objective-C:
```objc
// BEFORE (still compiles, but deprecated)
SFOAuthSessionRefresher *refresher = [[SFOAuthSessionRefresher alloc] initWithCredentials:credentials];
[refresher refreshSessionWithCompletion:^(SFOAuthCredentials *updated) {
    // handle success
} error:^(NSError *error) {
    // handle error
}];

// AFTER — success/failure blocks are (SFOAuthInfo *, SFUserAccount *) and (SFOAuthInfo *, NSError *)
[[SFUserAccountManager sharedInstance] refreshCredentials:credentials
    completion:^(SFOAuthInfo *authInfo, SFUserAccount *userAccount) {
        // handle success
    }
    failure:^(SFOAuthInfo *authInfo, NSError *error) {
        // handle error
    }];
```

## Step 8 — Handle DPoP now on by default

DPoP (Demonstration of Proof-of-Possession) is enabled by default in SDK 14.0. The property `usesDPoP` now defaults to `true`. If your app's Connected App is not configured for DPoP, login attempts will fail with a token exchange error.

**Option A — Opt out of DPoP (use during development/testing if the Connected App is not DPoP-enabled):**

```swift
override init() {
    super.init()
    SalesforceManager.initializeSDK()
    SalesforceManager.shared().usesDPoP = false  // remove before production
}
```

> Set `usesDPoP = false` immediately after `initializeSDK()`, before any auth flow begins.

**Option B — Enable DPoP on the Connected App and upgrade existing users:**

Configure the Connected App in Salesforce Setup to support DPoP, then use the migration API for users who previously authenticated without DPoP:

```swift
UserAccountManager.shared().upgradeToDPoP(userAccount,
    success: { authInfo, userAccount in
        // user's tokens are now DPoP-bound
    },
    failure: { authInfo, error in
        // handle upgrade failure (e.g. re-authenticate)
    }
)
```

`upgradeToDPoP(_:success:failure:)` is a method on `UserAccountManager` (Obj-C `SFUserAccountManager`), not `SalesforceManager`. The `success` block receives `(AuthInfo, UserAccount)` and `failure` receives `(AuthInfo, Error)`. Call it once per user account on first launch after the upgrade. Store a migration flag in `UserDefaults` keyed to the user's account ID so it is not called again on subsequent launches.

## Step 9 — Handle Advanced Authentication on by default for all hosts (if applicable)

Advanced Authentication (browser-based login via `SFSafariViewController`) is now enabled for **all** login hosts, including `login.salesforce.com`. In SDK 13, it was enabled only for specific hosts.

If your app must preserve the in-app `WKWebView` login flow:

```swift
SalesforceManager.shared().forceAdvancedAuthentication = false
```

Set this after `initializeSDK()` and before the first auth flow. Remove this line once the Connected App and user base are ready for browser-based login.

> **`forceAdvancedAuthentication` is deprecated in 14.0** — the header marks it `SFSDK_DEPRECATED(14.0, 15.0, "Advanced Authentication is becoming mandatory; this flag will be removed.")` (`SalesforceSDKManager.h:282`). It defaults to on, and setting it emits a deprecation warning. Treat the opt-out above as temporary — the flag will be removed in 15.0.

## Step 10 — Remove SalesforceSDKManager.isQrCodeLoginEnabled (if used)

Check for any remaining usage:

```bash
grep -rn 'isQrCodeLoginEnabled' --include='*.swift' --include='*.m' .
```

QR code login is always enabled in SDK 14.0 and the property was removed. Remove every call site, including any conditional that branches on its value.

> Generated apps (`forceios create`): this property appeared in `setupQrCodeLogin()` inside `AppDelegate.swift` as `MobileSyncSDKManager.shared.isQrCodeLoginEnabled = true`. Remove that line. The method itself can stay if it wires up UI; just remove the property assignment.

## Step 11 — Build verification

Run a full build and confirm it succeeds.

For CocoaPods apps:

```bash
xcodebuild \
  -workspace <ProjectName>.xcworkspace \
  -scheme <TargetName> \
  -sdk iphonesimulator \
  -destination 'platform=iOS Simulator,name=iPhone 16' \
  build | tail -5
```

For SPM apps (hand-managed or xcodegen):

```bash
xcodebuild \
  -project <ProjectName>.xcodeproj \
  -scheme <TargetName> \
  -sdk iphonesimulator \
  -destination 'platform=iOS Simulator,name=iPhone 16' \
  build | tail -5
```

Expected: `** BUILD SUCCEEDED **`

> **FMDB duplicate-class warning on SPM path:** You may see a message like `objc[]: Class FMDatabase is implemented in both SmartStore.framework/SmartStore and .../debug.dylib` in the build log. This is harmless — see [troubleshooting.md](troubleshooting.md) for an explanation.

If the build fails, see [troubleshooting.md](troubleshooting.md) or [breaking-changes.md](breaking-changes.md) for the specific error.
